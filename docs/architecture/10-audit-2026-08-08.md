## Purpose and target users (from README)

llm-swarm-router (netllm) is a **mesh router for local LLM backends**: a per-machine
agent that auto-discovers oMLX, Ollama, LM Studio and vLLM, meshes machines over LAN
(mDNS / subnet scan / static peers), and exposes one stable dual API surface
(OpenAI-compatible `/v1` + Anthropic Messages) to editors and agent harnesses.
Target users are **home-lab and multi-machine local-inference operators** who want
throughput that scales with hardware, 24/7 unattended operation, and optional cloud
fallback — without per-tool `base_url` juggling.

## Thesis

> After the F-24/F-25/F-26 consolidation the *request path* is no longer the risk.
> The remaining risk has moved to three places: **(1)** the surfaces the engine does
> not reach — bridges and translators that sit outside `SurfaceAdapter` and so are
> not covered by its invariants; **(2)** the **control plane's exposure**, where read
> gates degrade to no-ops under default configuration; and **(3)** the project's own
> **bookkeeping**, where a register that says RESOLVED is now load-bearing for
> decisions. Hypothesis: the consolidation holds, and the new defects cluster in
> bridge code and in claims-versus-reality rather than in routing.

**Verdict: confirmed, with one exception that outranks it.**

- **The consolidation held.** The engine/adapter split, the erosion gate and the
  146-vector corpus are all intact and enforcing. Axis-C extension is measurably the
  cleanest in the codebase. No per-surface failover loop was reintroduced.
- **Prediction (1) confirmed:** the two most serious functional findings (F-61, F-62)
  are both in bridge/translator code — `anthropic_bridge` and
  `openai_responses_bridge` — precisely where the `SurfaceAdapter` invariant does not
  reach. The F-24 sibling-asymmetry class survived the refactor by relocating.
- **Prediction (2) understated the problem.** F-59 is an S1: backend and cloud
  provider API keys are serialized in plaintext by `/netllm/v1/status` and
  `/netllm/v1/backends`, and `require_read_access` is a no-op when no cluster token is
  set — the default even on a LAN bind. This is worse than the thesis anticipated.
- **Prediction (3) confirmed but minor:** double-attribution and an unregistered
  finding, all S3.

# Findings

## F-59 · Backend and cloud-provider API keys are served in plaintext by /netllm/v1/status and /netllm/v1/backends, and gossiped to every peer

**Severity** S1 · **Area** standards · **Verdict** CONFIRMED · **Relation** NEW (F-13 follow-up — scope omission, same class as F-41)

- packages/netllm-core/src/netllm_core/models.py:505-531 — `class Backend(BaseModel)` declares `api_key: str = ""` (line 512) with no `Field(exclude=True)`, no `SecretStr`, and no field serializer
- packages/netllm-agent/src/netllm_agent/service/status.py:31 — `"backends": [b.model_dump(mode="json") for b in self.pool.backends]`
- packages/netllm-agent/src/netllm_agent/app.py:271 — `return {"backends": [b.model_dump(mode="json") for b in service.pool.backends]}`

`require_read_access` (app.py:120-146) is a no-op when `swarm.cluster_token` is empty — which is the default even for a LAN bind; `doctor_payload` only *warns* about that state (admin.py:47-51). So on the documented `netllm serve --host 0.0.0.0` swarm setup without a token, any host on the LAN can `GET /netllm/v1/status` and read the plaintext `api_key` of every configured backend, including `[cloud.providers.*]` rows holding real Anthropic/OpenAI/OpenRouter keys. Even with a token configured the keys still leave the machine: `start_gossip` pushes the identical payload to every peer, so one compromised or spoofed peer harvests the whole fleet's provider credentials, and `SwarmRegistry.fetch_peer` stores `data.get("backends", [])` verbatim (swarm.py:158-168) so the keys propagate transitively. F-13 added the authentication gate to this route and F-41 extended it to `/metrics`, but neither pass questioned the payload's contents — this is the scope omission underneath both.

**Fix:** Redact at the serialization boundary, not at each call site. Add a `@model_serializer`/`field_serializer` on `Backend` that emits `api_key` as `""` (or `api_key_set: bool`) for wire payloads, or introduce an explicit `Backend.public_dump()` and make status.py:31, app.py:271 and the gossip lambda use it. Add a red-green test asserting that `status_payload()`, `/netllm/v1/backends` and the gossip payload never contain a configured `api_key` value — the assertion F-40's fix note already recommended for `/netllm/v1/client-env` but that was never generalized. Treat any already-published keys as exposed on LANs where an untokened agent ran.

## F-60 · Configured cloud providers accept `netllm-local` as a real API key — the F-45 gate is missing on the [cloud.providers.*] path

**Severity** S2 · **Area** architecture · **Verdict** CONFIRMED · **Relation** F-45 follow-up — same invariant, the one remaining upstream path it was never applied to

- packages/netllm-agent/src/netllm_agent/service/cloud.py:161-180 — `api_key = provider_cfg.api_key or os.environ.get(provider_cfg.api_key_env,"") or os.environ.get(spec.api_key_env,"")`, then `if not api_key and provider_cfg.auth in ("api_key","plan_token"): continue`. No `is_netllm_placeholder_key` anywhere, unlike the legacy path 100 lines above it (cloud.py:41,44,53,56,112).
- Repro (real output): `OPENAI_API_KEY=netllm-local ANTHROPIC_API_KEY=netllm-local` + `cloud.providers.{openai,anthropic}.enabled=true` -> `svc._materialize_cloud_provider_backends()` yields `ROW: cloud-openai https://api.openai.com/v1 api_key= 'netllm-local' local= False` and `ROW: cloud-anthropic https://api.anthropic.com api_key= 'netllm-local' local= False`
- Real CLI output: `OPENAI_API_KEY=netllm-local netllm cloud list` prints `OpenAI | yes | global | openai | set` — the Key column claims 'set' (packages/netllm-cli/src/netllm_cli/commands/cloud.py:59-63)

F-45 established the invariant that a `netllm-`-prefixed key is never forwarded upstream as a real credential, and closed it on the legacy env/header path (`_openai_api_key`, `_anthropic_api_key`, `_legacy_anthropic_cloud_backend`). The `[cloud.providers.*]` materialization path — the one the whole `netllm cloud` UX drives users toward — never got the same treatment. A user who follows the documented client wiring (`export OPENAI_API_KEY=netllm-local`) and then runs `netllm cloud enable openai` gets a pooled, routable, non-local backend row carrying the sentinel as its credential. The `enabled but keyless -> skip` guard at cloud.py:176 is defeated because the placeholder is a non-empty string. Every request that reaches that row 401s upstream and consumes one slot of the failover budget; `netllm doctor`, `netllm cloud list`, the dashboard Cloud tab and macOS Settings all affirmatively report the key as set, so the user has no signal pointing at the cause. A secondary compounding path exists on macOS: apps/netllm-mac/Sources/Server/PythonRuntime.swift:87-92 only injects the Keychain key when `env[envVar]?.isEmpty != false`, so an inherited `OPENAI_API_KEY=netllm-local` silently suppresses a correctly-stored Keychain credential.

**Fix:** Apply `is_netllm_placeholder_key` at the three places that resolve a provider credential from the environment: the `api_key` assignment in `_materialize_cloud_provider_backends` (service/cloud.py:161-175), the same block in `cloud_provider_models_probe` (service/cloud.py:247-252), and the `has_key`/`api_key_set` computations in `cli/commands/cloud.py:59-63`, `cli/commands/cloud.py:250-257`, `admin.py:121-126` and `admin.py:196-205`. A shared `_resolve_provider_key(provider_cfg, spec) -> str` in `netllm_core` that filters placeholders would keep all six in step. Treating a filtered key as absent makes the existing `continue` at cloud.py:176-180 fire, which is already the correct behaviour, and makes doctor say 'missing' instead of 'set'. Separately, drop the `env[envVar]?.isEmpty != false` precondition in PythonRuntime.swift:87 (or extend it to reject `netllm-` values) so an explicitly stored Keychain key wins over an inherited placeholder.

## F-61 · Mid-stream upstream failure on /v1/responses is reported to the client as response.completed — a successful-looking truncated answer

**Severity** S2 · **Area** routes · **Verdict** CONFIRMED · **Relation** NEW (register-level) — pinned as a known divergence in the contract vector only; F-24 sibling-asymmetry class, in the bridge layer the SurfaceAdapter invariant does not reach

- packages/netllm-agent/src/netllm_agent/service/surfaces/base.py:381-384 — OpenAIDialectAdapter.mid_stream_error_frame returns `data: {"error": {"message": ...}}` then `data: [DONE]`
- packages/netllm-core/src/netllm_core/openai_responses_bridge.py:256-265 — the translator only reads `choices[0].delta`; an `{"error": ...}` chunk parses, yields nothing, and the following `[DONE]` hits the `break` at :260-261
- packages/netllm-core/src/netllm_core/openai_responses_bridge.py:456-464 — after the loop it unconditionally emits `response.completed` with `status` derived only from finish_reason

Every other streaming surface ends a post-first-byte failure honestly: chat emits an error chunk plus [DONE] (base.py:381), Messages emits `event: error` plus `event: message_stop` (base.py:443, the D9 flip). /v1/responses drops the error frame on the floor because the translator only inspects `choices[0].delta`, then emits `response.completed` carrying whatever partial text arrived before the drop. A Codex-style client therefore accepts a truncated answer as a complete one — silent data loss rather than a visible failure. The router side is correct (the backend is marked failed and netllm_requests_total{status=error} increments per the vector), so the defect is purely client-facing. It is documented inside the vector note but carries no F-number and appears in neither the findings register nor the closure roadmap, so nothing schedules it.

**Fix:** Give the translator an error arm: when a chunk contains a top-level `error` key, emit `response.failed` (or `response.incomplete` with an `error` object) and return, instead of falling through to `response.completed`. Update stream-midstream-drop-responses-s.json to the corrected frames and file it in the findings register so it stops living only as a vector comment.

## F-64 · Translated /v1/messages streaming arm drops input_tokens: client sees 0 and the router accounts 0 prompt tokens

**Severity** S2 · **Area** routes · **Verdict** CONFIRMED · **Relation** F-33 follow-up (residual gap on the one arm F-33's vector does not cover)

- packages/netllm-core/src/netllm_core/anthropic_bridge.py:109 — `input_tokens = 0`
- packages/netllm-core/src/netllm_core/anthropic_bridge.py:178 — `input_tokens = usage.get("prompt_tokens", input_tokens)` (assigned, never read again)
- packages/netllm-core/src/netllm_core/anthropic_bridge.py:171 — message_start emits `"usage": {"input_tokens": 0, "output_tokens": 0}` unconditionally

On /v1/messages streaming against an openai-format backend (the common case: Claude Code pointed at a local llama.cpp/Ollama/LM Studio row), the bridge parses the upstream's prompt_tokens into a local `input_tokens` variable and then never emits it. The client's message_start carries input_tokens 0 and message_delta carries only output_tokens, so an Anthropic SDK client tracking usage reports zero input tokens for the whole request. The same zero propagates into the router: engine.StreamSession folds `adapter.extract_stream_usage` over the *emitted* (post-translation) frames, so netllm_prompt_tokens_total, the telemetry payload and the Serving UI all record 0 prompt tokens for this arm. The native anthropic arm is unaffected (upstream supplies real input_tokens in message_start), and the non-streaming translated arm is unaffected — this is the F-33 target "full accounting everywhere incl. stream usage parse" landing on three of four arms.

**Fix:** In translate_openai_stream_to_anthropic, carry input_tokens into the emitted frames: either buffer message_start until the first usage-bearing chunk is seen, or (simpler, and what the Anthropic wire tolerates) include `"input_tokens": input_tokens` in the final message_delta usage object alongside output_tokens. Add a contract vector `stream-usage-chunk-parsed-messages-s-translated-arm` mirroring the native-arm vector so the asymmetry is pinned.

## F-95 · save_config writes the file holding the cluster token and provider API keys non-atomically, and chmods 0600 only after the write

**Severity** S3 · **Area** standards · **Verdict** CONFIRMED · **Relation** NEW (F-48 follow-up — atomic-write discipline was applied to stats.json but not to config.toml)

- packages/netllm-core/src/netllm_core/models.py:677-690 — `cfg_path.write_text(tomli_w.dumps(payload), …)` followed by `if os.name == "posix": os.chmod(cfg_path, 0o600)`
- packages/netllm-agent/src/netllm_agent/telemetry.py:137-152 — the contrasting discipline for the *less* valuable file: tmp file in the same directory, `os.replace(tmp_path, self._stats_path)`, with the comment "a crash mid-write can never leave a truncated stats.json (F-48)"
- packages/netllm-agent/src/netllm_agent/app.py:340-360 — `POST /netllm/v1/admin/config` calls `save_config_patch` on every dashboard/menubar settings change, so this path runs interactively, not just at install time

Two distinct issues in four lines. First, `write_text` truncates in place: a crash, ENOSPC or power loss between truncate and flush leaves a partial or empty config.toml, and `load_config` (models.py:660-664) will then either raise on malformed TOML or silently return a default `NetllmConfig()` — losing the cluster token, every configured backend and every cloud API key. F-48 established write-then-rename as the standard here for stats.json, a file the code itself calls "a convenience total, not an audit log"; the file that actually holds the secrets did not get the same treatment. Second, on first creation the file exists with mode 0666 & ~umask (0644 under the common umask 022) for the window between `write_text` and `os.chmod` — a local unprivileged reader can win that race and read the freshly minted cluster token. **Fix:** Mirror telemetry.py: write to `cfg_path.with_suffix('.toml.tmp')` in the same directory, `os.chmod(tmp, 0o600)` on the tmp file *before* writing (or open it via `os.open(..., O_CREAT|O_EXCL, 0o600)`), then `os.replace(tmp, cfg_path)`. That fixes truncation and the permission window in one change and keeps the two persistence paths consistent.

## F-96 · secrets.compare_digest is applied to raw header text, so a non-ASCII Authorization header raises TypeError and returns 500 from unauthenticated routes

**Severity** S3 · **Area** standards · **Verdict** CONFIRMED · **Relation** NEW

- packages/netllm-agent/src/netllm_agent/app.py:102-106 — `secrets.compare_digest(auth, f"Bearer {token}")` and `secrets.compare_digest(request.headers.get("x-api-key", ""), token)` on unvalidated header strings
- packages/netllm-core/src/netllm_core/source_identity.py:46-52, 91-99 — `_extract_key` pulls the same header, and `_secret_satisfied` calls `secrets.compare_digest(key_secret, required)` on it; the resolve_source docstring at line 67 explicitly promises "Never raises"
- packages/netllm-agent/src/netllm_agent/admin.py:33-34 and app.py:405-408 (heartbeat) use the same primitive on the same input

HTTP header values are latin-1 on the wire, so any byte in 0x80-0xFF reaches Python as a non-ASCII `str`. `secrets.compare_digest` rejects that input rather than returning False. The result is that an unauthenticated remote client can turn any token-gated route (`/metrics`, `/netllm/v1/status`, `/v1/*` under `require_token_for_inference`, `/netllm/v1/heartbeat`) into a 500 with a logged traceback by sending one malformed header byte. It is not an auth bypass — the request still fails closed — but it is unauthenticated remote error-log amplification and it violates the documented no-raise contract of `resolve_source`, which sits on the inference hot path. It is also the kind of thing basedpyright will not catch and no current test covers.

**Fix:** Add a single helper (e.g. `netllm_core.platform.secure_eq(a, b)`) that encodes both operands with `.encode('utf-8', 'replace')` before `compare_digest` and returns False on any encoding failure, and route app.py:102-106, admin.py:33-34, app.py:405-408 and source_identity.py:98 through it. Add a test sending a raw non-ASCII Authorization header to a gated route and asserting 401/403 rather than 500.
