## Divergence list (= refactor requirements)

Each item is a place where a shared concern is implemented differently or missing; a unified `_RequestPlan` + `_run_with_failover` (the F-24 design, 07-findings-register.md:677–693) must make each an explicit, parameterized decision.

1. **Success accounting — 3 tiers.** Full (mark_success + REQUESTS_TOTAL + latency + tokens + `_request_count`): C-NS s:1051–1062, EMB s:1320–1331, M-NS s:1674–1685. Partial (no tokens, no `_request_count`): C-S via s:2032–2037. **Nothing**: M-S s:1904–1910. → **F-33, in-flight**: remediation gives M-S the `_stream_with_metrics` treatment and has both streaming wrappers parse the final usage-bearing SSE chunk (09:143–157) — after it lands the refactor's target is "full accounting everywhere incl. stream usage parse".
2. **Failure accounting.** C-S outer except records neither `_mark_backend_failure` nor error-status REQUESTS_TOTAL (s:1173–1192; delegated to s:2040–2043 — the exact divergence F-24 documented, 07:685–688). M-S marks failure directly (s:1914) but never increments REQUESTS_TOTAL error. Non-stream paths do both inline.
3. **Streaming route-layer error handling is dead code (F-32, in-flight).** a:409–424/436–449/473–486 catch around `StreamingResponse` generators that haven't run yet ⇒ capacity/exhaustion errors on `stream=true` become HTTP 200 + aborted body. The planned fix (pre-flight attribution/admission/routing/first-backend before constructing the response, 09:139–141) **changes the loop shape of all three stream paths** — the refactor must be designed against the post-F-32 split (plan/first-connect phase vs. stream phase), not the current all-in-generator shape.
4. **Capability guard.** C-NS/C-S reject non-chat models pre-routing (s:992/1109); M-NS/M-S post-payload-mutation (s:1724/1833) with an Anthropic-typed twin (s:611–620); EMB has **no guard at all** — a chat model routed to /v1/embeddings burns the whole retry budget.
5. **Shard context** only on chat paths (s:1002/1119); EMB/M-NS/M-S pass `None` (s:1292/1760/1871), so `batch_shard`/deterministic placement silently degrades there.
6. **Cloud fallback topology.** OpenAI paths: cloud row is a first-class strategy candidate via `extra_candidates` (s:1030). Messages paths: anthropic rows are excluded from the strategy loop and appended as an ordered fallback tier (s:1746–1750 + 1785/1861–1899) — two different "cloud last" mechanisms, the M-S one via a bespoke `candidates_exhausted`/`fallback_iter` state machine unique to that function.
7. **Attempt cap semantics.** `max_attempts = max(len(pool.backends), 1)` (s:1013/1130/1280/1752/1857) excludes request-scoped `cloud_extra`; M-NS/M-S then exceed the cap through the fallback tier while C-NS/C-S/EMB cannot.
8. **`tried` pre-seeding** as a format filter: EMB seeds pool anthropic rows (s:1281–1283); messages seed pool **and** cloud_extra anthropic rows (s:1746–1750/1851–1855); chat seeds nothing — same set doing double duty (failure exclusion + format exclusion) with three different initializations.
9. **Requested-model restore**: present in four paths (s:1048, 1167, 1317, 1667–1672) — missing in M-S (translated stream emits the rewritten model, s:2013–2016). *(Adjacent, same cell: the M-S mid-stream `event: error` frame had no terminator event, where C-S has always closed with `data: [DONE]`.)* → **RESOLVED, plan §3 Phase 7**: `MessagesAdapter.restore_stream_line` restores the requested name on `message_start` frames — by *value*, because the translated arm's name is the bridge's copy of the upstream chunk's own `model`, not the adapter's resolved one — and `mid_stream_error_frame` now emits `event: message_stop` after the error event. Re-recorded under a declared `D9` across the five annotated vectors; the paired `D10` cell (the served name on the *upstream* call) is byte-identical.
10. **Payload mutation timing**: messages rewrite `payload["model"]` up-front (s:1722–1723/1831–1832); chat/embeddings keep the payload immutable and rewrite per backend (s:1042–1046) — matters for retries across backends with different aliases.
11. **Error propagation asymmetry**: OpenAI routes forward upstream 400/404 (a:422); the messages route forwards any `AnthropicUpstreamError` status but flattens `OpenAIUpstreamError` (from translated backends) to 502 (a:485–486). Keyless exhaustion is 401 on messages (s:1804–1808/1947–1951) vs 404-model-not-found on OpenAI paths (s:1087/1202/1355). (Adjacent: F-38 — all bodies are `{"detail"}` not OpenAI/Anthropic error shapes, 09:207–217.)
12. **Header normalization** duplicated at the messages route only (a:471) — harmless today, but a trap.
13. **Peer-forward loop-guard headers** only exist on the OpenAI upstream constructor (s:682–715); the Anthropic-format arm never attaches them (s:1970–1977/1999–2006) — currently safe only because peers are always openai-format rows.
14. **EMB scenario classification** runs the chat classifier with `api_format="openai"` (s:1254–1259) — scenario rules written for chat silently apply to embedding traffic.
15. **Not currently divergent but coupled to in-flight work**: `TypeError` from the F-30 SDK bug (`messages_stream` passes `stream=` to `.stream()`, 09:88–99) is not an `AnthropicUpstreamError`, so it escapes M-S's except (s:1911) and surfaces through the F-32 dead zone as a 200/aborted stream; **F-35, in-flight**: EMB's SDK call splats raw payloads (`netllm-sdk-openai/client.py:79–84` per 09:180–184) while chat is adapted — after remediation, payload adaptation should be a per-endpoint property of the plan, not of the SDK call site.
16. **RESP-S records no success accounting at all.** *(Line refs in this item alone are against the post-remediation tree `f349526`, not the `64f14a4` baseline used everywhere above: `_record_stream_success` is F-33 code that does not exist at `64f14a4`, and the contract vectors that pin D16 were recorded on `f349526`.)* `proxy_responses_stream` (s:1312–1322) delegates to `proxy_chat_completion_stream`, whose per-attempt `_stream_with_metrics` (s:2129–2160) does its accounting *after* the `async for` over the upstream chunks finishes: `_record_stream_success` s:2148 (impl s:249–276 — `pool.mark_success`, `REQUESTS_TOTAL{status="ok"}`, `REQUEST_LATENCY`, prompt/completion token counters, `telemetry.record_usage`, `self._request_count += 1`) then `_mark_shard_success` s:2155. The Responses translator never lets that code run: `translate_chat_stream_to_responses` **`break`s** out of `async for raw in chunks` the moment it sees `data: [DONE]` (`netllm_core/openai_responses_bridge.py:259–261`), abandoning the underlying async generator mid-iteration — the eventual `aclose()`/GC raises `GeneratorExit` at the suspended `yield`, so neither the post-loop accounting in `_stream_with_metrics` nor the `return` at s:1258 executes. On a fully successful RESP-S request this means: `routed_counts` empty, no `netllm_requests_total{status="ok"}`, no `netllm_request_latency_seconds_count`, no token counters, `_request_count` unchanged. The **failure** side is intact — the `except OpenAIUpstreamError` arm (s:2156–2160) fires inside the loop, so `_mark_backend_failure` + `REQUESTS_TOTAL{status="error"}` are recorded normally — so RESP-S telemetry shows errors and never successes. C-S with an identical backend script records the full set; this is a fourth, empty tier beneath divergence 1's three, and F-33 did not reach it because the hole is in the bridge, not in the loop. It also contradicts the "RESP … inherits every C-NS/C-S cell verbatim" claim above. Pinned by the five `*-responses-s` 200-vectors annotated `["D16"]`. → **RESOLVED, plan §3 Phase 7**: the fix is structural rather than a patch to the bridge. `engine.StreamSession` reads one chunk ahead of the consumer — it pulls the next upstream event, settles the attempt's accounting, and only then hands on the pending chunk — so the accounting is already written by the time `data: [DONE]` leaves, and a consumer that abandons the generator at its own terminator cannot strand it. `proxy_responses_stream` additionally `aclose()`s the chat generator in a `finally`, which makes the *release* half (pool slot, per-source admission) prompt instead of GC-timed. RESP-S now records the identical success set C-S records, asserted by `test_metrics_parity.test_responses_stream_success_accounting_matches_chat_stream`.

17. **Batch-ledger candidate list now honors `exclude_ids` — chat `batch_shard` failover order and attempt count change.** *(Introduced by Phase 5, not present at either `64f14a4` or `f349526`; declared here as the refactor's own divergence.)* The batch-ledger arm of `_select_backend_for_request` (`packages/netllm-agent/src/netllm_agent/service.py`, the `strategy == "batch_shard"` + `shard.batch_id/index` branch) used to hand `pool.backends_for_model(...)` to the ledger raw — it was the single selection route that ignored `exclude_ids`. Phase 5 filters it, because [D5] feeds shard context to EMB/M-NS/M-S and [D8] moved dialect eligibility into `schedule.ineligible_ids`: an unfiltered list would let the ledger assign an anthropic-format row to a `/v1/embeddings` request. **The claim that this is invisible on the chat paths is false.** `BatchRequestLedger.reassign_failed` (`packages/netllm-agent/src/netllm_agent/shard.py:72–83`) locates the current backend by *index* — `urls = [b.base_url for b in backends if b.enabled]`; `try: pos = urls.index(current_url) except ValueError: pos = -1`; `for url in urls[pos + 1:]`. Filtering the just-failed backend out of `candidates` makes `.index()` raise, so `pos = -1` and the retry walk **restarts at the head of the candidate list** instead of continuing past the failed position. Empirically, with three chat rows `[alpha, beta, gamma]`, `default_strategy = "batch_shard"` and `x-netllm-shard-index: 2` (so `assign()` lands on `gamma`, `index % len(urls) != 0`): before, a `gamma` failure ended the request after **one** attempt with the upstream error (`urls[3:]` is empty, `reassign_failed` returns `None`, the loop breaks); after, the walk restarts at `alpha` and the request makes up to **three** attempts, returning 200 when any earlier row succeeds. Only assignments to a non-first row are affected — for shard index 0 the order is `[alpha, beta]` either way, which is why the five pre-existing (happy-path) `batch_shard` vectors could not see it. Defensible and kept: the old forward-only walk gave a shard assigned to the last-position backend *zero* failover, and post-D5 it could re-dispatch to a dialect-ineligible row. Pinned by `tests/contract/vectors/routing-failover/chain-batch-shard-reassign-restarts-at-head-chat-ns.json` and `-chat-s.json`.

18. **The two model matchers become one; the `model_pools` invocation arm gains the tag-prefix/casefold-tag-prefix matching candidacy always had.** *(Introduced by plan §3 Phase 8b, not present at `64f14a4` or `f349526`; declared here as the refactor's own divergence — the deliberate retirement of the F-25 regression trap recorded in Phase 0.)* At HEAD the router answered the model-name question **twice, with two different algorithms**. Matcher A, candidacy: `RouterPool.backends_for_model` → `_serves_model` (p:455–462) — fully casefolded, exact-or-`name:tag`-prefix, run first over `model_names_for` (aliases) and then, for a pool member, over `pool_models_for_backend`. Matcher B, invocation: `AgentService._model_for_backend` (s:533–570) — alias exact → alias tag-prefix → alias casefold → `RouterPool.resolve_via_pool` (p:433–453) → passthrough, where `resolve_via_pool` had **no tag-prefix arm at all** (exact over pool models, then casefold-exact over served IDs). The alias half of the two agreed; the pool half did not, and the gap is reachable: a backend serving `poolmodel:7b` in a pool whose `models` lists `poolmodel` is a candidate for *any* requested name (A's tag-prefix arm accepts it) and is then invoked with the **raw requested name it does not serve** (B's pool arm returns `None`). Recorded as-is in Phase 0 as `tests/contract/vectors/naming-cloud-guards/naming/naming-f25-trap-pool-tag-prefix-disagree.json`, paired with `naming-f25-trap-alias-tag-prefix-agree.json` where the same name in `model_aliases` makes B's alias arm — which *does* have tag-prefix — agree. **Phase 8b deletes both matchers** in favor of `netllm_core.model_resolution.ModelResolver`, one walk — alias exact → alias tag-prefix → alias casefold → group exact → group tag-prefix → group casefold → catalog passthrough — from which `serves()` is *derived* (it is "the walk did not fall through", plus the unchanged blind-catalog p:522–525 and auth-gated-skip p:510–521 rules) rather than computed separately. Candidacy is unchanged as a **set**: A's alias union and the resolver's alias arms accept exactly the same backends, and A's pool union and the resolver's group arms likewise (asserted over generated corpora with the frozen legacy matchers as oracles in `tests/test_model_resolution_property.py::test_candidacy_matches_legacy_oracle`). What moves is the **invoked name** in the group arm alone: the trap vector's upstream call carries `poolmodel:7b` instead of `anything-goes`, making it identical to its alias control. A full-suite shadow run of the resolver beside both legacy matchers (1056 tests) produced **exactly one** disagreement — that vector — and zero candidacy disagreements. Pinned by `naming-f25-trap-pool-tag-prefix-disagree.json`, annotated `["D18"]`; the invariant behind it (a selected backend is always invoked with a name it advertises) is asserted directly by `test_resolver_is_internally_coherent`.

Constant across all paths (safe to hoist verbatim): attribution/scenario counting once per request (s:739–786), admit-before-first-await + finally-release (s:799–823), capacity classification (s:498–509 → p:39–55, statuses 409/429/503/507), `_offload_if_probing` selection, `yielded_any` no-replay guard on both streams (s:1132/1858), pin/strategy/local-only header plumbing (s:717–737 → rp:60–191).
