# Compatibility policy

What netllm promises across versions, and — separately — **what is actually
enforced in this tree today**. The two columns differ, and the difference is
the point of this document. A promise with no gate behind it is a plan, and
`packages/netllm-cli/src/netllm_cli/commands/join_swarm.py` already tells
operators to verify "a compatible netllm version" without anywhere defining
what that means.

## Four version axes, never conflated

| Axis | Where it lives | Scheme | State |
|---|---|---|---|
| **App version** | `pyproject.toml`, asserted by `tests/test_version_sync.py` | 4-part `X.Y.Z.N` | **exists** |
| **Telemetry schema** | `packages/netllm-agent/src/netllm_agent/telemetry.py` | monotonic int | **exists** — the template the others were meant to copy |
| **Config schema** | a `schema_version` key in `config.toml` | monotonic int | **does not exist** |
| **Wire generation** | `/netllm/v1/status`, heartbeat, mDNS TXT | monotonic int | **does not exist** |

Two of four. `config_schema.get_version()` is an **app-version ETag for the
form document**, not a config schema version; conflating them is the specific
mistake this table exists to prevent.

## The promises

### `/v1/*` dialect routes — additive only, no sunset

**Enforced.** `tests/contract/routes.json` is an *exact set*, regenerated by
`scripts/generate-routes-json.py --check` in `./scripts/ci.sh lint`. Deleting
`/v1/responses` fails the build. The predecessor listed 17 of ~28 routes and
asserted presence only, so a deletion was CI-green.

Response shapes are pinned by 373 contract vectors. Any change requires a
declared divergence id in `tests/contract/allowed-divergences.txt`, which
`tests/contract/test_divergence_lint.py` enforces.

### `/netllm/v1/*` — additive within a wire generation

**Not enforced.** There is no wire generation number to be "within". The
route *set* is gated exactly as `/v1/*` is, so a removal fails the build; what
is missing is the versioned overlap window (old shape served with
`"deprecated": true` for one minor after a generation bump).

In practice: treat `/netllm/v1/*` as additive-only and assume every client
you cannot see is older than you.

### Config — forward-compatible in both directions

| Direction | Promise | State |
|---|---|---|
| Old agent + new config | unknown keys **preserved**, never dropped on save | **enforced** — `tests/test_config_forward_compat.py` |
| New agent + old config | migrations run | **not built** — there is no migration rail |

The preserved half is the load-bearing one and it is real. Every write path —
the dashboard **Save**, macOS Settings **Save**, `netllm config import`,
`netllm join`, `POST /netllm/v1/admin/config` — keeps keys this build does not
model, re-emits them, and logs one warning naming them. Unknown
`[cloud.providers.<id>]` subtrees are preserved and reported by
`netllm doctor` rather than filtered away.

That is what makes a rolling upgrade non-lossy: upgrade one machine,
configure a provider there, press **Save** on an older machine, and the newer
machine's keys survive.

The migration half is not built. **Today the only safe config change is an
additive one.** Renaming or removing a key has no rail: no `schema_version`,
no `config_migrations.py`, no `config.toml.bak-v{n}`, no
`netllm config migrate --dry-run`.

### Mesh skew — N−1 fully supported, N−2 degraded, beyond that a doctor error

**Not enforced, and not implemented.** No peer-skew policy is applied
anywhere. `PeerRecord.version` rides heartbeats and empty means "an older
peer, treat as unknown, never warn". There is no mixed-version test lane and
no interop-vector corpus under `tests/contract/`.

Two related gaps worth knowing about before you rely on skew behaviour:

- **Version comparison is two algorithms with no shared corpus.**
  `netllm_core.update.compare_versions` and the Swift updater implement
  ordering independently. Python's mis-orders prereleases
  (`1.0.0-rc.1` → `[1,0,0,1]`), masked only because `fetch_latest_release`
  filters prereleases out — so the exposed case is an operator *running* one.
- **Upgrade ordering: gateway first.** `packages/netllm-agent/src/netllm_agent/service/swarm_tasks.py` makes the gateway
  authoritative for routing strategy, so a newer gateway can serve older
  peers and not the reverse; a strategy an older peer does not know degrades
  to that peer's default rather than corrupting it. This is a reasoned
  position, not a measured one — the competing design argued gateway *last*
  from the same evidence. It is written down here so it can be challenged
  with data.

### Deprecations — every removal announced with a clock

**Not built.** There is no `deprecations.toml` under `docs/`, no `DEPRECATIONS`
registry, no `DeprecationWarning` on config load, and `netllm doctor` lists
no deprecated keys. Shims are removed when somebody remembers.

## What to do today

| You want to… | Do |
|---|---|
| Add a config key | Additive only. Follow [extending/04-cli-and-control-plane.md](extending/04-cli-and-control-plane.md) |
| Rename or remove a config key | **Wait for the migration rail**, or accept that old configs break |
| Add a `/netllm/v1/*` field | Additive. Older clients must ignore unknown keys |
| Remove any route | Don't. `routes.json` will stop you, correctly |
| Change a response shape | Declare a divergence id in `tests/contract/allowed-divergences.txt` and write a release note |
| Upgrade a mesh | Gateway first. Verify with `./netllm status` on a peer |
